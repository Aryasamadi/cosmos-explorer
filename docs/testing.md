# تست، اعتبارسنجی و کنترل کیفیت

## دستورها

```bash
npm run lint
npm run typecheck
npm run test        # حالت watch برای توسعه
npm run test:ci     # اجرای یک‌بارهٔ تست‌های Vitest
npm run test:e2e    # تست مرورگری موبایل با Playwright/Chrome
npm run build
VITE_BASE_PATH=/cosmos-explorer/ npm run build
VITE_BASE_PATH=/cosmos-explorer/ npm run check:pages
```

روی Git Bash ویندوز، برای جلوگیری از تبدیل مسیر توسط MSYS از
`MSYS_NO_PATHCONV=1 VITE_BASE_PATH=/cosmos-explorer/ ...` استفاده کنید؛ در Linux/CI
نیازی نیست.

`npm run test:e2e` از Chrome نصب‌شده روی سیستم استفاده می‌کند (`channel: chrome`).
اگر Chrome نصب نباشد، می‌توانید `npx playwright install chromium` را اجرا کنید و
پیکربندی را به Chromium تغییر دهید؛ در GitHub Actions از Chrome نصب‌شدهٔ runner استفاده
می‌شود.

CI همین مراحل را پیش از هر انتشار اجرا می‌کند و علاوه بر آن یک build با
`VITE_BASE_PATH` مسیر GitHub Pages می‌سازد و با `npm run check:pages` بررسی می‌کند
همهٔ ارجاع‌های محلی دارایی‌ها با همان base شروع شوند. انتشار GitHub Pages فقط پس از
موفقیت lint، typecheck، تست، build و این بررسی انجام می‌شود.

## تشخیص فاز ۰، فاز ۱، M2 و یکپارچگی

علاوه بر تست‌های production، یک suite تشخیصی جدا در `diagnostics/` وجود دارد:

```bash
npm run test:diagnostics:typecheck
npm run test:diagnostics:astronomy
npm run test:diagnostics:browser
```

این suite شامل تست‌های ناوبری، نور/نجوم، cache، geolocation شبیه‌سازی‌شده،
baselineهای تصویری و کنترل‌های P1 است. در فاز ۱، expected-failهای astronomy و
geolocation برطرف شدند. M2 نیز چهار نقص ناوبری (انتخاب اولیهٔ Earth، بازگشت
focus/pose پس از Earth→Moon→Earth، و حفظ state بین Free/Sky) را رفع کرد؛ این چهار
تست اکنون بدون `test.fail` و با همان assertionهای قبلی pass می‌شوند. P1 نیز
هم‌ترازی فاز ماه، سایه‌گذاری شبانه/خاموش‌کردن OSM، attribution شرطی، برچسب اجرام و
راهنمای مقیاس لمسی را پوشش می‌دهد. suite مرورگری اکنون **۴۴ تست عادی** دارد
(۷ ناوبری، ۸ cache، ۱۵ geolocation، ۱ محیط، ۱۱ visual، ۱ integration و ۱ P1) و هیچ
expected-fail پنهان یا حذف‌شده‌ای ندارد. این suite **در CI معمول اجرا نمی‌شود**؛
بنابراین سبزبودن CI فعلی به معنی پوشش آن نیست. جزئیات در
[گزارش فاز ۰](mission-006-diagnostics.md)، [گزارش فاز ۱](mission-007-phase1.md)،
[گزارش M2](mission-010-m2.md)، [گزارش یکپارچگی M1+M2](mission-011-integration.md) و
[گزارش P1](mission-014-p1.md) آمده است.

  `mission-014-p1-correctness` آماده‌اند اما merge یا deploy نشده‌اند.

  ۳ تست مرورگری جدید برای اندازه/دسترس‌پذیری اضافه شد. در زمان M1، ۱۸۲ unit و
  ۱۱ E2E سبز بودند.

  Earth→Moon→Earth، Free→Sky→Free و نبود خطای کنسول/شبکه در

- P1: فاز نمایشی ماه با فاز ژئومرکزی هم‌تراز شد (خطای frame/مرجع در شش رقم اعشار

  پایداری بازتولید شدند.

  **۱۴/۱۴**، diagnostics typecheck سبز. E2E نهایی ۱۱/۱۱ با timeout محیطی ۱۸۰s؛

  سبز شدند؛ assertionها تغییر نکردند.
- `lint`: بدون خطا و بدون warning.
- `typecheck`: بدون خطا با TypeScript strict.
- `build`: موفق (شامل build با base path صفحات و `check:pages`).

کاشی‌های OSM بخشی از build نیستند و فقط در زمان اجرا و هنگام نزدیک‌شدن دوربین دریافت
می‌شوند. کاشی‌های NASA بخشی از build هستند اما در استارتاپ دانلود نمی‌شوند؛ در نمای
کلی هیچ درخواست `/earth-detail/` در تست Playwright ثبت نشد و انتقال اولیهٔ اندازه‌گیری‌شده
حدود ۹۱۳ کیلوبایت بود (با OSM مسدود). کاشی‌های NASA با همان میزبان برنامه سرو می‌شوند.

این اعداد حجم انتقال را نشان می‌دهند، نه FPS یا مصرف باتری. هیچ benchmark عملکردی روی
دستگاه واقعی انجام نشده است.

## مرجع مستقل JPL Horizons

نمونه‌های منبع در `src/test/referencePositions.ts` ثبت شده‌اند. تنظیمات پرس‌وجو:

```text
format=text
EPHEM_TYPE=OBSERVER
CENTER=coord@399
COORD_TYPE=GEODETIC
REF_SYSTEM=ICRF
APPARENT=AIRLESS
QUANTITIES=4,20
```

این تنظیمات، آزیموت/ارتفاع ظاهری بدون شکست جو و برد را برای ناظر ژئودتیک می‌دهد.

### تلورانس‌ها

- آزیموت/ارتفاع: `< 0.02°`
- فاصلهٔ نسبی: `< 3×10⁻⁴`
- Polaris: اختلاف ارتفاع با عرض ناظر `< 1.5°` (به دلیل فاصلهٔ ۰٫۷۴ درجه‌ای از قطب)

این تلورانس‌ها برای نمایش آموزشی انتخاب شده‌اند و ادعای ناوبری دقیق نمی‌کنند. مقایسه
فقط پیاده‌سازی و یکپارچه‌سازی را می‌سنجد.

## آزمون مرورگر شبیه‌سازی‌شده

در تاریخ ۲۰۲۶-۱۰-۲۲ با Chrome Headless (نسخهٔ ۱۵۰) و viewport موبایل **۳۹۰×۸۴۴**
(devicePixelRatio=2، locale=fa-IR، timezone=Asia/Tehran) سناریوهای زیر اجرا شد:

1. بارگذاری کاوش آزاد، نمایش زمین، انتخاب ماه و بازشدن پنل اطلاعات.
2. ورود دستی مختصات تهران، تمرکز دوربین روی مکان و بارگذاری تدریجی کاشی‌های OSM تا
   سطح ۱۴ در یک جلسهٔ تعاملی محدود؛ مشاهدهٔ نشانگر وسط‌چین، برچسب «تهران» و راه‌های
   واقعی.
3. تغییر به آسمان واقعی، ورود دستی مختصات و نمایش snapshot علمی.
4. فعال‌سازی حسگر با رویدادهای شبیه‌سازی‌شدهٔ absolute و مشاهدهٔ وضعیت «حسگر روشن».
5. فعال‌سازی دوربین با دستگاه دوربین جعلی Chrome، نمایش video و سپس خاموش‌کردن آن.
6. تغییر زمان به یک لحظهٔ روز و مشاهدهٔ خورشید/مریخ و گرادیان روز.
7. بررسی نبود خطای کنسول و نبود سرریز افقی صفحه.

هشت جریان در `e2e/mobile.spec.ts` به‌صورت خودکار و در CI اجرا می‌شوند: جریان پایهٔ
رابط کاربری/آسمان، مکان شبیه‌سازی‌شدهٔ دستگاه با دقت ۳۰ متر، شکست عمدی کاشی‌ها،
آزمون مات‌بودن کره هنگام بارگذاری/شکست/زوم نزدیک، **پیشرفت تصویر ماهواره‌ای و افزایش
لبه‌ها**، **شکست هم‌زمان OSM و تصویر با کرهٔ مات**، **لغو درخواست معلق با بازگشت به
نمای کلی** و **سازگاری layout دسکتاپ ۱۲۸۰×۸۰۰**. آزمون مات‌بودن و آزمون تصویر ابتدا
یک خشکی روزانه را از فهرست نامزدها انتخاب می‌کنند، درخواست‌های OSM را مسدود می‌کنند،
کاشی‌های تصویر را برای گرفتن نمونهٔ پایه نگه می‌دارند، پیکسل‌های canvas را نمونه‌گیری
می‌کنند و سپس کاشی‌ها را آزاد می‌کنند. در آزمون دوم edge-energy پس از دریافت تصویر
باید واقعاً بیشتر شود. برای رعایت سیاست OSM، هیچ تست خودکاری به سرور کاشی واقعی
درخواست نمی‌فرستد؛ درخواست‌ها در Playwright مسدود یا با پاسخ محلی جایگزین می‌شوند.
بارگذاری واقعی OSM فقط در یک بررسی تعاملی محدود و برای اعتبارسنجی بصری انجام شد.

این آزمون‌ها **آزمون گوشی واقعی نیستند** و نمی‌توانند دقت قطب‌نما، جهت صفحه،
کالیبراسیون دوربین یا رفتار iOS Safari را تأیید کنند. هیچ ادعای تأیید سخت‌افزاری در
README یا رابط کاربری مطرح نشده است.

## اندازه‌گیری عملکرد (۲۰۲۶-۱۰-۲۳)

محیط: build تولیدی سروشده با `vite preview` روی localhost، Chrome headless، GPU
مجتمع Intel HD Graphics 520 با ANGLE/D3D11، viewport ۳۹۰×۸۴۴، DPR ۲، بدون throttle
شبکه. این اعداد برای بررسی رگرسیون چیدمان درخواست‌ها هستند، نه benchmark گوشی.

| سنجه | مقدار |
| --- | --- |
| navigation → صحنهٔ پایه آماده (هر چهار بافت) | ~۱٫۷۴ ثانیه |
| ثبت مکان → loading chip جزئیات | ~۱٫۵۰ ثانیه |
| ثبت مکان → آماده‌شدن جزئیات | ~۲٫۳۷ ثانیه (شامل fly-to ۱٫۱۵s و settle ۲۶۰ms) |
| درخواست یکتای تصویر NASA در تمرکز | ۲ (level 5؛ ۱۳۸٬۴۵۲ بایت) |
| درخواست تصویر NASA در نمای کلی | ۰ |
| انتقال اولیهٔ منابع (JS/CSS/بافت/قلم؛ OSM مسدود) | ~۹۱۳ کیلوبایت |
| focus تا آماده‌شدن تصویر (سه اجرا) | ۱٫۶۳–۱٫۷۷ ثانیه |
| زمان decode/نمایش پس از آزادشدن کاشی معلق | ~۰٫۲۲ ثانیه |
| edge-energy پایه → تصویر (همان نما) | ۰٫۴۶۱ → ۲٫۴۲۳ (≈۵٫۳ برابر) |

زمان focus شامل fly-to ۱٫۱۵s و settle ۲۶۰ms است. آماده‌شدن صحنه در سه اجرا
~۱٫۰۴–۲٫۱۶ ثانیه بود؛ اجرای اولِ بدون cache کندتر و اجراهای بعدی سریع‌تر بودند.
کاشی‌های OSM در این سنجش مسدود بودند و کاشی‌های NASA از localhost سرو شدند. یک
بررسی تعاملی محدود با OSM واقعی، z8 و ۱۵ کاشی یکتا را نشان داد؛ این یک نمونه است،
نه benchmark.

سناریوی قبلی با کاشی مصنوعی و تأخیر ۱۲۰ms (۹ کاشی z7 و z14) دیگر معیار این نسخه
نیست. رندر نرم‌افزاری SwiftShader همچنان بسیار کندتر است (۵ تا ۷ ثانیه برای آماده‌سازی
صحنه در اندازه‌گیری قبلی)؛ اعداد به GPU حساس‌اند و به گوشی تعمیم داده نمی‌شوند.
تأخیر واقعی OSM، شبکهٔ سلولی، مصرف باتری، FPS و حافظهٔ GPU دستگاه واقعی اندازه‌گیری
نشده است.

## محدودیت‌های تست فعلی

- WebGL در jsdom اجرا نمی‌شود؛ تست‌های UI عمداً مسیر fallback را می‌سنجند. صحنه‌های
  Three.js با آزمون مرورگر واقعی (شبیه‌سازی‌شده) بررسی شده‌اند، نه در Vitest.
- آزمون Playwright جریان پایهٔ UI، geolocation شبیه‌سازی‌شدهٔ Chromium و شکست کاشی را
  پوشش می‌دهد؛ سناریوهای حساس به سخت‌افزار (حسگر، دوربین، iOS) به‌صورت خودکار
  شبیه‌سازی نمی‌شوند.
- میزان موفقیت/شکست درخواست‌های واقعی OSM در آزمون خودکار بررسی نمی‌شود (عمداً)؛
  رفتار خطای کاشی با مسدودسازی شبکه آزمون شده است.
- حداکثر جزئیات نقشهٔ OSM در نمای ۳۹۰×۸۴۴@2x حدود z15 است؛ آزمون تعاملی ۰٫۴٫۰
  z8 را دید. سطوح بالاتر از بودجهٔ viewport ادعا نمی‌شوند. جزئیات تصویر NASA نیز
  سقف منبع ۱۶۳۸۴ روز و ۱۳۵۰۰ شب دارد.
- آزمون مات‌بودن از پیکسل‌های اسکرین‌شات استفاده می‌کند و به GPU/رندر واقعی وابسته
  است؛ در محیط بدون WebGL به‌صورت skip گزارش می‌شود.
- هیچ benchmark رسمی FPS، مصرف حافظه یا باتری روی دستگاه‌های مختلف انجام نشده است.
  اعداد محلی بخش قبل با سخت‌افزار/شبکهٔ مشخص ثبت شده‌اند.
- دقت موقعیت ماه/سیارات فقط در نمونه‌های JPL ثبت‌شده سنجیده شده است؛ پوشش جهانی
  ادعا نمی‌شود.
- رفتار iOS Safari برای `requestPermission` و `webkitCompassHeading` با unit test و
  شبیه‌سازی منطقی بررسی شده، نه روی دستگاه واقعی.
- متن‌های فارسی و چیدمان با بررسی بصری در مرورگر ارزیابی شده‌اند؛ آزمون خودکار a11y
  کامل وجود ندارد.

## افزودن تست

- منطق خالص را در همان پوشهٔ ماژول با `*.test.ts` قرار دهید.
- برای محاسبات نجومی، نمونهٔ مرجع بیرونی (در صورت وجود) و تلورانس را در همان فایل ثبت
  کنید؛ تست را فقط برای سبز شدن ضعیف نکنید.
- برای تست UI، `@testing-library/react` و `userEvent` استفاده کنید و به CSS یا WebGL
  واقعی وابسته نشوید.
- هر تغییر در کاتالوگ باید تست‌های یکتایی شناسه، منبع و اعتبار عددی را حفظ کند.
